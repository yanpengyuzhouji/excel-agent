# 单实例数据卷备份恢复演练

当前服务使用SQLite和本地文件，需要一致保存元数据库、源附件、草稿、查询库、会话、报告及日志。不要只备份一个database.sqlite，也不要逐个复制正在写入的数据库充当一致性备份。

## 当前可执行方式

经批准的维护窗口内，在项目目录执行：

```powershell
.venv/Scripts/python.exe -X utf8 scripts/drill_live_backup.py --confirm-cold-backup
```

没有`--confirm-cold-backup`不会执行。脚本会短暂停止当前固定核心容器，完成冷备即启动原服务；即使打包失败也尝试恢复原服务。它会创建可删除的合成核验会话，然后在新卷恢复，原卷从不作为解包目标。

需Docker Desktop Linux容器、宿主机httpx及空闲18093端口。此脚本针对本项目单实例布局；其他主机/端口/容器名需先核对，不可照抄不明卷名。

## 验证顺序

停止写入 → 停服 → 全卷只读清单/冷备 → 原服务启动 → tar校验值 → 新卷解包 → 启动前文件哈希和SQLite校验 → 同镜像恢复副本启动 → 会话/附件/查询/报告验证 → 清理合成核验数据和恢复副本。

每次生成独立`data/business_acceptance/live-backup-时间/`目录：

- `data-volume.tar`：保留的全卷备份，包含业务数据。
- `source-manifest.json`、`restored-manifest.json`：文件哈希、大小、数据库完整性及表行数。
- `drill.json`：每项验证、实际停服/恢复时间、tar SHA256及清理结果。

SHA256用于校验传输损坏，不是加密或数字签名。tar包只用于可信来源恢复，不能将来历不明的归档直接解包到服务目录。

## 恢复失败时

原服务已在打包后立即启动，恢复副本的失败不覆盖原数据。先检查drill.json错误和原服务健康状态，不执行down -v、volume prune或删除原卷。保留备份和验证记录用于分析。

## 正式运维仍需补齐

本次实际演练通过记录见[RC16放行验证](production-gate-rc16-2026-10-16.md)。它不等于已经建立自动备份、异地灾备或新Ubuntu主机恢复。

应另行确定备份周期、保留份数、可接受数据丢失时间RPO和恢复时间RTO；将备份加密后复制到不同主机/受控存储，保护访问权限。部署镜像、配置、.env密钥需分别安全保存，不能提交Git或打入公共镜像。恢复到新主机后还要验证真实模型凭证、网络、网关和权限设置。
